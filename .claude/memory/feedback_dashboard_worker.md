**Neither the dashboard API nor the worker auto-reloads — both are plain long-running processes.** A `git pull` or local code edit has zero effect on either until it's killed and relaunched. Always run `bash scripts/restart_dashboard.sh` after pulling or editing anything under `core/`, `adapters/`, or `services/dashboard_*.py`.

**Why the API lost `--reload` (2026-07-10):** it used to auto-reload, but on this pod the reloader repeatedly hung at "Waiting for connections to close" whenever a browser tab held an open SSE stream (`/api/jobs/*/stream`) — a known `uvicorn --reload` failure mode with long-lived connections. This silently froze the *entire* dashboard: Cancel/Approve buttons stopped working (the click never reached a live server), and running jobs looked "stuck" with no way to tell they weren't — happened 3 times in one session, each from an unrelated commit. `--reload` was removed entirely; both processes now need an explicit restart for any change, no exceptions.

**Restarting the worker orphans ANY job it's currently handling** — mid-stage (rendering) or mid-poll (waiting on an approval), doesn't matter, both used to leave the job's queue action stuck `status=claimed` forever. **Fixed (2026-07-10)**: `DashboardRepository.reclaim_stale_claims()` runs on every worker startup, detects `job_queue` rows claimed by a worker with no recent heartbeat, and requeues them — the pipeline's own resume logic (keyed on cached per-stage artifacts) picks up right where the dead worker left off. Still prefer restarting only when nothing's actively running (avoids wasted GPU work re-doing an in-flight stage), but it's no longer a manual-recovery situation if you don't.

**If a restart doesn't seem to take effect, check for a zombie holding the port before assuming the fix is wrong.** A stuck or leftover process can keep the listening socket even after its cmdline no longer matches `pgrep -f`'s pattern in `stop_matching()`, silently serving stale code forever while new start attempts fail in the background with `[Errno 98] Address already in use` (curl still gets 200s — from the zombie). Check `ss -ltnp | grep <port>` for the actual PID. `scripts/restart_dashboard.sh` also kills by port (`stop_port()`) as a second layer, but if you ever bypass that script and restart manually, check for this.

**Approval polling had a real bug class, now fixed**: `DashboardRepository.get_pending_approval(job_id)` filters `WHERE status='pending'` in SQL — the instant an approval is resolved (approved/rejected), it vanishes from that query. Three separate poll loops used to call this to check for a decision on an approval they'd already created (`dashboard_approval_adapter.py`, `dashboard_image_approval_adapter.py`, `dashboard_worker.py`'s transcript review gate) — meaning a resolved approval was invisible to the poller, and the job hung silently until a 4h timeout. Fixed by adding `get_approval(approval_id)` (fetches by ID regardless of status) and switching all three loops to it. If you add a new approval gate, poll with `get_approval(approval_id)`, never `get_pending_approval`.

**Retry endpoint**: `POST /api/jobs/{id}/retry` re-queues a `failed` job for the SAME phase (not the next one, unlike `/advance`). Works because `script_plan`/`render`/`assemble` already skip any stage whose artifact JSON exists on disk — so retry picks up right after the last stage that actually succeeded, it doesn't redo the whole phase. Only accepts `status=failed`; a job stuck in `pending_*_approval` or `running` with no live worker no longer needs a manual DB reset (see reclaim_stale_claims above) — just restart the worker and it requeues itself automatically.

**GPU services need explicit per-job lifecycle management, not just adapter-level unload/load.** Three separate incidents (2026-07-09/10), same root shape: something GPU-resident that a job's *own* adapters don't manage was left stranded, OOMing a later job. (1) ComfyUI's idle LTX/Flux model was invisible to `ensure_video_model_unloaded`/`prepare_*_model` whenever a job's own render/video adapter wasn't ComfyUI-backed — fixed with `core.gpu_sequencer.free_comfyui()`, called unconditionally before the render loop regardless of adapter selection. (2) Fish S2's own CUDA allocator retains memory across synthesis calls that `POST /unload` + `torch.cuda.empty_cache()` can't reclaim (~63GB resident observed vs ~20GB fresh-process baseline) — fixed by killing the whole process (`stop_fish_s2_process()`) in `dashboard_worker`'s per-job `finally`, respawned on demand (`ensure_fish_s2_process_running()`) only when a job actually needs it. (3) Wan's video model was never unloaded anywhere in the mainline pipeline *after* Phase A's one-time pre-render-loop hook — it stays resident through assemble/publish and beyond for every outcome (completed/failed/cancelled) — fixed with `unload_wan()`, also unconditional in the same `finally` block. **Cancelling a job does NOT stop server-side GPU computation for HTTP-based adapters** (Wan, ComfyUI) — only the client-side call is abandoned; the server keeps computing (confirmed: a cancelled job's Wan generation kept running for 16+ minutes afterward, GPU pinned at 100%, `/unload` rejected with `409 Conflict` the whole time). If VRAM doesn't free up after a cancel, check for this — the fix is killing that service's process, not waiting.
