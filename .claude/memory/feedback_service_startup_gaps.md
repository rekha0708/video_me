`bash scripts/start_services.sh` sometimes fails to bring up ComfyUI, Fish Audio S2, Wan2.2, or MuseTalk even though torch and ~140 other system packages are intact — it's usually just 1-2 missing pip packages, not a full environment wipe.

Seen on 2026-07-03: system Python was missing `sqlalchemy` (breaks ComfyUI's `app/assets` import chain), and both `.venv_fish_s2` and `.venv_wan` were missing `click` (breaks uvicorn's CLI entrypoint even though uvicorn itself was installed).

Seen on 2026-07-10: `.venv_musetalk` was missing `transformers`, `einops`, AND `rich` (the last one a transitive dep of `mmengine`, not in MuseTalk's own requirements.txt) — despite `setup_gpu.sh`'s `setup_musetalk()` explicitly listing `transformers`/`einops` in its pip install command, so a from-scratch run of that script *should* have installed them; exact cause of the gap on this pod is unconfirmed (partial/interrupted install run is the leading guess, not verified).

**Much bigger lesson from the 2026-07-10 incident — a silent-failure bug amplified this into a whole-session-invisible outage:** `core/workflow.py`'s `_generate_shot_video` caught `lip_sync` failures and fell back to the raw un-synced clip (correct resilience behavior — don't fail the whole job over lip-sync), but unconditionally reported `stage_completed`/"lip sync done" to the dashboard regardless of whether it actually succeeded or silently fell back. Every single `/lipsync` call failed with `ModuleNotFoundError` (100% failure rate, confirmed via `grep -c` in musetalk.log) for the *entire* session, and the dashboard reported success on every one — an operator asked "why is lip-sync completely out of sync" believing it was a MuseTalk *quality* problem on singing audio, when there had been literally zero lip-sync applied to any output all session. Fixed: the fallback path now emits `stage_failed` (maps to `DashboardEventLevel.ERROR`, renders as ✕ in the dashboard timeline) instead of `stage_completed`. **The general principle: any exception-swallowing fallback path must report its own outcome honestly to the dashboard — "recovered gracefully" and "the user should know this happened" are not the same requirement, and conflating them turns a visible service outage into an invisible, session-long "worse quality than expected" mystery.**

**Why:** Only the Ollama binary is documented as wiped on RunPod pod restart ([[project_video_me]]); in practice small individual pip packages can also go missing from system Python and from /workspace venvs between sessions, cause unclear.

**How to apply:** If `start_services.sh` reports ComfyUI/Fish/Wan/MuseTalk not responding, check `/workspace/logs/{comfyui,fish_s2,wan,musetalk}.log` for `ModuleNotFoundError` before assuming a bigger problem. Fix is a quick targeted `pip install <missing-pkg>` (system pip3 for ComfyUI, `.venv_fish_s2/bin/pip` / `.venv_wan/bin/pip` / `.venv_musetalk/bin/pip` for those), then re-run start_services.sh — do NOT reinstall from scratch. Also: Fish Audio S2 takes ~60-90s to load the 20GB model and warm up before `/health` responds — a "did not respond after 60s" warning from the script doesn't always mean failure, check the log for a benign "loading weights" state before treating it as broken. **More broadly: if a pipeline stage has a try/except fallback, don't trust its dashboard "completed" status alone as proof the primary path worked — check the actual service's own log for errors, especially for lip_sync/MuseTalk specifically, since its failure mode is silent-and-plausible-looking rather than a visible job failure.**
